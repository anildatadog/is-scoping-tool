Three architecture approaches

Same decisions: single app · two phases · FastAPI backend · Cloud Run. Different in how frontend and backend are packaged and deployed.

A

Monorepo — two Cloud Run services

One GitHub repo with frontend/ (Next.js) and backend/ (FastAPI). Two separate Cloud Run services — is-scoping-frontend (public, handles OAuth) and is-scoping-backend (internal, API only). James owns frontend/, Anil owns backend/. Backend never publicly exposed.

Pros

  • James has total frontend freedom
  • Backend stays internal — no public auth on API
  • One PR can touch both sides
  • Shared API types in shared/

Cons

  • Two Cloud Run deploys to manage
  • Service-to-service auth to wire up (Cloud Run invoker)

⭐ Recommended

B

Single container — nginx proxy

One Cloud Run service running both Next.js (port 3000) and FastAPI (port 8000) inside the same container. nginx routes /api/* to FastAPI, everything else to Next.js. Single deploy.

Pros

  • One Cloud Run service — simplest ops
  • No cross-service auth needed
  • Closest to current single-container model

Cons

  • nginx config adds complexity
  • Two runtimes in one container — harder to scale independently
  • Trickier local dev
C

Separate repos — two Cloud Run services

Frontend and backend in separate GitHub repos. James fully owns the frontend repo. Same two-service Cloud Run setup as A.

Pros

  • Cleanest ownership split
  • James iterates UI without touching backend repo

Cons

  • Harder to keep API contract in sync
  • Cross-cutting changes need two PRs
  • More repo admin overhead
